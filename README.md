# Process automation system of the MTD department

Сервіс для обробки та виконання запитів. Працює з клієнтом по захищеному каналу (ZeroMQ з протоколом шифрування CURVE)

---

## 🛠 Технологічний стек

Проект розроблено на базі **Python 3.12**. Усі модулі системи розділені за функціональними напрямками.

### 1. Мережева взаємодія та Асинхронність
* `zmq` (PyZMQ) — організація зв'язку між клієнтом та сервісом. Використовує вбудовану потокову автентифікацію (`ThreadAuthenticator`) та протокол шифрування **CURVE** (генерація ключів через `zmq.auth`).
* `aiohttp` & `asyncio` — асинхронне паралельне виконання I/O операцій та завантаження даних.
* `requests` — виконання синхронних HTTP-запитів.

### 2. Керування завданнями та Потоки
* `APScheduler` (`BackgroundScheduler`) — планувальник для запуску періодичних та фонових завдань за розкладом.
* `threading` — використання системних потоків та подій (`threading.Event`) для безпечного скасування та паралельного виконання важких тасок без блокування ZeroMQ-сервера.
* `concurrent.futures` (`ThreadPoolExecutor`) — пул потоків для оптимізації викликів.

### 3. Робота з даними та DBMS
* `SQLAlchemy` (ORM) — побудова моделей даних (`declarative_base`) та виконання безпечних SQL-запитів через абстракцію двигуна (`create_engine`, `text`).
* `pandas` — високошвидкісна пакетна вставка (Bulk Insert) великих масивів даних у базу та швидке формування Dataframe на основі підготовлених структур.
* `json` — серіалізація та десеріалізація структур даних і конфігів.

### 4. Безпека, Криптографія та Деплой
* `win32crypt` (модуль `pywin32`) — використання Windows Data Protection API (DPAPI) для безпечного шифрування та дешифрування секретів локально на рівні ОС.
* `hashlib` — генерація криптографічного хешу за допомогою алгоритму SHA-256 для створення додаткової ентропії (entropy) при захисті ключів через Windows DPAPI.
* `Nuitka` — компілятор, що використовується для збирання проєкту у захищений бінарний файл.
* `python-dotenv` (`load_dotenv`) — використовується тільки під час розробки для емуляції змінних оточення. У продакшн-білді повністю замінюється захищеним сховищем секретів.

### 5. Моніторинг та Системні утиліти
* `logging` — розгалужена і кастомізована система логування.
* `RotatingFileHandler` — автоматична ротація файлів логів для запобігання переповненню диска (обмеження: до 10 МБ на файл, максимум 25 архівних копій).

## 🚀 Підготовка оточення та встановлення

### 1. Сервісний обліковий запис

Проект розгортається в інфраструктурі підприємства як системна служба Windows за допомогою утиліти **NSSM (Non-Sucking Service Manager)**.
Служба працює від імені виділеного сервісного облікового запису.

Для надання необхідних прав:
1. Відкрийте Локальну політику безпеки (`secpol.msc`).
2. Перейдіть: **Local Policies** ➔ **User Rights Assignment**.
3. Додайте обліковий запис до політики **Log on as a service** (Вхід у систему як служба).

### 2. База даних (MS SQL)

Потрібно підготувати таблиці та обліковий запис для роботи сервісу. Створити `schedule_info` та `export_Py` і надати відповідні права.

В цілях безпеки, це не автоматизувалося. Сервісному обліковому запису надаються відповідні права на кожну таблицю, а не на всю базу.

### 3. Ініціалізація захищеного сховища секретів (Secure Vault)

Усі чутливі дані шифруються за допомогою Windows DPAPI та прив'язуються до пароля сервісного акаунту.

Під час первинного налаштування або оновлення конфігурації у захищене сховище мають бути внесені такі обов'язкові параметри:

* **Системні налаштування та мережа:**
  * `LOG_LEVEL` — рівень деталізації логів (`INFO`, `DEBUG`, `WARNING`).
  * `SERVICE_ADDR` — мережева адреса та порт для ZeroMQ-сервера.
  * `ALLOWED_IPS` — білий список IP-адрес, яким дозволено підключатися до сервісу.
  * `CURVE_SECRETKEY` — секретний ключ шифрування CURVE для захисту ZMQ-каналу.
* **Авторизація в зовнішніх системах (API):**
  * `LOGIN` & `PASS` — облікові дані для авторизації на HR API.
  * `LOGIN_URL` — адреса API для проходження автентифікації.
  * `PERSONELL_DATA_URL` & `PERSONELL_DATA_URL_W` — базові API для отримання даних.
* **Параметри бази даних (MS SQL / SQLAlchemy):**
  * `DB_USER` & `DB_PASSWORD` — доступи до бази даних.
  * `TABLE_NAME` — назва таблиці для імпорту/синхронізації даних.

### 4. Реєстрація служби через NSSM
Служба ініціалізується з обов'язковою передачею пароля сервісного акаунту в ізольоване середовище процесу (`AppEnvironmentExtra`), що необхідно для динамічного розшифрування секретів сховища під час роботи.

**Основні параметри реєстрації служби:**
* Шлях до виконуваного файлу.
* Обліковий запис для запуску від імені.
* Змінна середовища для розшифрування (пароль_акаунту).

**Команди керування службою (через CMD/PowerShell від імені Адміністратора):**
* Запуск служби: `nssm start SyncService`
* Зупинка служби: `nssm stop SyncService`
* Перезапуск служби: `nssm restart SyncService`
* Перевірка статусу: `nssm status SyncService`

## ⚡ Продуктивність та Оптимізація (Bulk Upload)

У системі реалізовано високоефективний механізм пакетного збереження великих масивів даних в базу. При прямій пооб'єктній вставці через ORM процес імпорту **200 000+ рядків (об'ємом близько 4 ГБ)** тривав **понад 1,5 години** і критично навантажував систему.

Перехід на пакетну обробку (Bulk Insert) за допомогою `pandas` та метаданих `SQLAlchemy` дозволив скоротити час виконання операції **до менш ніж 10 хвилин**.

### Ключові фактори прискорення:
1. **Потокова фільтрація:** Функції `filter_data_for_model` та `clean_data_record` миттєво очищують та підготовлюють сирі дані (користувачів) у пам'яті, відсікаючи зайве ще до етапу взаємодії з СКБД.
2. **Паралельний мапінг типів:** Програма динамічно зчитує типи колонок безпосередньо з ORM-моделі `Employees.__table__.columns` та передає їх у вигляді словника в метод `to_sql`. Це позбавляє базу даних необхідності самостійно вгадувати типи та витрачати на це час.
3. **Chunk size оптимізація:** Завантаження виконується цілісними пачками (`chunksize=len(users)`), мінімізуючи кількість транзакцій та мережевих затримок (round-trips) між сервісом та базою даних.

## ⚙️ Додавання нового функціоналу

За обробку запитів, запуск функцій в потоці та спілкування з клієнтами, відповідає модуль `handlers.py`.

**Основний життєвий цикл запиту:**
1. `handle_request` — миттєво приймає запит від ZMQ-клієнта та формує швидку відповідь (наприклад, статус `processing`).
2. `execute_task_thread` — запускає важкі фонові функції в окремому потоці безпечно для основного сервісу.
3. `run_in_thread` — виконує безпосередній алгоритм дій (виклик бізнес-логіки з модулів) та динамічно керує статусами виконання.

### Інструкція для розширення системи:
Щоб додати нову команду або автоматизацію:
1. Створіть новий модуль у структурі `src/` (або додайте функцію в існуючий).
2. Додайте нову умову/кейс в обробник `handle_request` модуля `handlers.py`.
3. Огорніть виклики вашої бізнес-функції через `execute_task_thread`, щоб забезпечити її асинхронне виконання без блокування сервісу.
